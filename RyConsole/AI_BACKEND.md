# AI 后端配置规格（RyConsole AI 探针迭代器）

> 版本：v1.0（2026-09-13）
> 目标：**同一个 OpenAI 兼容客户端**，可切换「局域网本地模型」与「免费云模型」，不改代码逻辑。

---

## 0. 架构原则：只写一个客户端

三家的接口形状都是 **OpenAI Chat Completions**，所以：

```
POST {BASE_URL}/chat/completions
Headers: Content-Type: application/json  (+ Authorization: Bearer <KEY> 若有)
Body:    {"model": "...", "messages": [...], "temperature": 0.2, "stream": false}
```

客户端里只暴露三个可配项：`base_url` / `api_key` / `model`。
**换后端 = 换配置，不换代码。** 这是本次选型的全部意义。

---

## 1. 后端 A：局域网 + 本地模型（首选：快、免费、数据不出门）

| 项 | 值 |
|---|---|
| base_url | `http://<你电脑的主机名>.local:11434/v1` |
| api_key | 任意字符串（Ollama 不校验，但客户端别省这个头） |
| model | 见下方选型 |

### ⚠️ Ollama 默认只监听 127.0.0.1 —— 必须做这三步

1. **让它监听所有网卡**：设置用户环境变量 `OLLAMA_HOST=0.0.0.0:11434`，然后**完全退出并重启 Ollama**（托盘图标右键退出，不是关窗口）。
2. **放行防火墙**：Windows 防火墙给 11434 加入站规则（专用网络即可）。
3. **确认主机名可用**：iPad 上能解析你的 `.local` 名（你现有代码里已经在用 `DESKTOP-4EILO2C.local`，说明这条路是通的）。

> **为什么推荐用 `.local` 主机名而不是裸 IP？**
> `NSAllowsLocalNetworking` 对 `.local` 与非限定主机名是明确覆盖的，而 RFC1918 裸 IP（192.168.x.x）在实践中"通常可以"但**不是文档明确保证**。
> 用 `.local` 最稳。若你坚持用裸 IP 且被拦，再加 ATS 例外域。

### 模型选型（RTX 4060 Laptop / 8GB 显存）

| 模型 | 显存占用 | 评价 |
|---|---|---|
| `qwen2.5:1.5b`（你现在的） | ~1GB | ❌ **太弱**：写 iOS 探针会瞎编 API，只会绕圈 |
| **`qwen2.5-coder:7b`（Q4）** | ~4.7GB | ✅ **推荐起点**：代码模型，能塞进 8GB，写 JS 探针够用 |
| `qwen2.5-coder:14b`（Q4） | ~9GB | ⚠️ 溢出到内存，速度掉一个档；想更强再上 |

```bash
ollama pull qwen2.5-coder:7b
```

## 2. 后端 B：免费云模型（本地不够力时的备选）

> ⚠️ 免费模型名与额度**会变**，以下为 2026-09 检索结果，接入前以官网为准。

| 服务商 | base_url | 免费情况 | 备注 |
|---|---|---|---|
| **硅基流动 SiliconFlow** | `https://api.siliconflow.cn/v1` | 多款永久免费模型；免费层 1000 RPM / 50K TPM | 限流最宽松；含 Qwen3-8B、DeepSeek-R1-Distill-7B 等 |
| **智谱 GLM** | `https://open.bigmodel.cn/api/paas/v4` | Flash 系列免费 | 中文与代码都不错；免费档并发低（约 1 并发） |
| **阿里云百炼** | `https://dashscope.aliyuncs.com/compatible-mode/v1` | qwen-turbo 等轻量模型有免费额度 | 模型种类最多 |
| **魔搭 ModelScope** | `https://api-inference.modelscope.cn/v1` | 每日约 2000 次请求（单模型约 500） | 需绑定阿里云账号 |

全部为 **https** → **无需任何 ATS 例外**。

## 3. 后端路由建议（写进客户端的默认策略）

```
1) 先试 本地 Ollama（局域网）
   - 连不上 / 超时 2s → 直接降级，不要卡住
2) 本地返回但质量差（生成代码解析失败 ≥3 次）→ 提示可切云端
3) 云端作为"离线/兜底"：需要联网，注意免费档的并发与速率限制
```

**关键：本地优先。** 探针循环会高频调用（每轮一次），云端免费额度会很快烧完，且设备信息不该无谓外传。

---

## 4. 回喂策略（决定成败的那一步）

每轮把**结构化结果**喂回去，而不是只丢报错文本：

```json
{
  "goal": "探测 AppleH1 可用 selector",
  "round": 3,
  "attempts": [
    {"selector": 0, "inputs": "[]", "ret": "0xe00002e2",
     "meaning": "kIOReturnNotPermitted", "panicked": false},
    {"selector": 1, "inputs": "[]", "ret": "0xe00002bc",
     "meaning": "kIOReturnUnsupported", "panicked": false}
  ],
  "notes": ["该服务族此前需要 entitlement，无 entitlement 时一律 NotPermitted"]
}
```

**必须内置一份错误码字典**（`0xe00002e2 → kIOReturnNotPermitted`、`0xe00002bc → kIOReturnUnsupported`、`0xe00002c7 → kIOReturnBadArgument` …）。
有没有这份字典，AI 的迭代效率差一个数量级 —— 没有它，模型只会反复撞同一面墙。

---

## 5. 安全约束（客户端必须硬编码，不可由 AI 决定）

1. **只读优先**：默认只发查询类调用；写/擦除类 selector 进黑名单。
2. **速率限制**：每轮之间留间隔；连续失败 N 次自动停。
3. **每次调用前落盘**：写 checkpoint（可复用已验证的 `v3_methodfuzz_checkpoint.json` 机制），崩溃后能续跑。
4. **危险面留人工**：AI 只负责"提出候选 + 跑 + 读结果"，真正危险的那一步由人决定。
5. **运行前确认设备上无不可替代数据**。

## 6. 后端 C：iPad 端上跑模型（可行，但要认清它能做什么）

### 6.1 硬约束（实测数据）

- **内存规则**：Q4 量化约 **0.6 GB / 1B 参数**；但实际占用 = 权重 + KV cache + 运行时缓冲 + 系统，**要留 50~100% 余量**。
- **iPadOS 会限制单个 App 的内存上限，超了直接杀进程**（不是变慢，是闪退）。
- 本机（iPad 10 / A14 / **4GB**）的合理区间：

| 模型规模 | Q4 权重 | 本机可行性 | 速度参考（A14/A15 同量级，Metal） |
|---|---|---|---|
| 0.5B–1B | 0.3–0.8 GB | ✅ 舒服 | 生成 **30 tok/s 左右** |
| 1.5B–2B | ~1 GB | ✅ 可以 | 约 20–30 tok/s |
| **3B** | ~2 GB | ⚠️ 能跑但偏紧 | 生成 **约 15 tok/s** |
| 7B | ~4.5 GB | ❌ **不要想**（必被杀进程） | — |

- 苹果**系统自带的端上模型（Foundation Models 框架）在本机大概率不可用**：它需要 Apple Intelligence，而后者门槛是 A17 Pro / M 系列芯片，A14 不在列。
  自验方法：去「设置」看有没有 Apple Intelligence 开关 —— 没有就是不能用，只能自己带推理引擎。
- **要端上跑模型，就得把推理引擎（llama.cpp 静态库 + Metal）编进 App** —— 这属于原生改动，**必须重编 IPA**（不像 JS 层那样可以热改）。这是与后端 A/B 最大的成本差异。

### 6.2 关键设计原则：给端上模型「选择题」，不给「作文题」

1B–3B 模型**写不出正确的 iOS 探针 JS**（会瞎编 API）——这一点你说得对，"太傻"。
但它在**有限选项的判断**上相当可靠。所以任务要这样切：

| 任务类型 | 例子 | 交给谁 |
|---|---|---|
| **开放生成**（写代码） | "写一段探测 AppleH1 selector 的 JS" | ❌ 端上做不了 → **网络大模型** |
| **有限判断**（选择题） | "这个返回码属于：权限被拒 / 不支持 / 参数错？" | ✅ 端上合适 |
| **选下一步** | "下一步该试：换 selector / 换服务 / 停止？" | ✅ 端上合适 |
| **结构化整理** | 把日志压成 JSON 摘要 | ✅ 端上合适 |
| **离线兜底** | 网络断了，至少继续判断+记录，不至于全瘫 | ✅ 端上唯一不可替代的价值 |

**结论：端上模型不是用来写代码的，是用来当「决策与解析」那一半大脑的。**

### 6.3 与后端 A/B 的关系（不是二选一，是分工）

```
                    ┌─ 需要「写代码」 ──→ 网络（A: 局域网 Ollama / B: 免费云）
  一轮迭代的请求 ──┤
                    └─ 需要「判断/解析/记录」──→ 端上（C: iPad 本地 1B~3B）
```

- 你原本那句「iPad 本地模型可以联网，不然太傻」——**方向完全正确**，而且这就是最终形态：
  **端上负责"想"，网络负责"写"，谁都不缺。**
- ⚠️ 但有一个现实约束：4GB 内存下，**端上模型 + RyConsole 的 IOKit/JS 探针同时跑有 OOM 风险**。
  所以端上模型要么选 **0.5B–1B**，要么**在一轮探针跑完后卸载再加载**，不要全程常驻。

### 6.4 落地顺序（建议）

1. **第一版**：先不做端上模型。用网络模型（A 或 B）把闭环跑通，**先证明这个循环有用**。
2. **第二版**：加端上 1B 级模型（如 Qwen2.5-1.5B-Instruct-Q4 / Llama-3.2-1B）做**离线降级 + 决策层**。
3. **第三版**：若端上「判断层」被证明有效，再考虑端上为主、云端只负责写代码。
